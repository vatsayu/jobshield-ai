# JobShield AI

> **AI-assisted security verification for job seekers**

JobShield AI is a security-focused application that helps job seekers analyze **job URLs, recruiter messages, and recruitment emails** for potential cybersecurity and trust-related risk indicators.

The system analyzes available evidence, explains detected signals, presents a structured risk assessment, and recommends safer next actions.

> 🚧 **Active Development**
>
> JobShield AI is an actively developed project. Some planned capabilities, including external AI provider integration, persistence, OCR, and production deployment, are not yet implemented.

---

## Core Principle

```text
Analyze → Explain → Provide Evidence → Recommend Safe Action
```

JobShield AI is designed to help users understand potential risks rather than make unsupported claims.

A suspicious indicator does not automatically mean that a recruiter, organization, or job posting is fraudulent.

---

# Product Boundary

JobShield AI is a **security verification and analysis tool**.

It is **not**:

- A job provider
- A recruitment agency
- A job marketplace
- A placement consultancy
- A recruiter
- An employment guarantee service

The application does not guarantee that a job opportunity is legitimate.

Its purpose is to provide security-oriented analysis and evidence so that users can make better-informed decisions themselves.

# Current Features

## 1. Job / URL Analysis

Users can submit a job or recruitment URL for analysis.

The URL analysis engine currently evaluates technical and structural indicators including:

- URL normalization
- Hostname characteristics
- Suspicious TLD indicators
- Suspicious URL encoding
- URL userinfo
- Hyphenated hostname signals
- Long hostname-label signals
- Network target validation
- Redirect safety
- URL fetching safety
- Loopback address protection
- Private network protection
- Cloud metadata protection

The analysis produces a structured risk assessment.

---

## 2. Recruiter Message Analysis

Users can submit recruiter messages for analysis.

The deterministic analysis engine evaluates predefined security-related indicators such as:

- Suspicious requests
- Recruitment payment requests
- Currency-based payment requests
- Urgency-related signals
- Potentially risky instructions
- Other predefined message risk indicators

The system returns evidence and recommended actions.

---

## 3. Recruitment Email Analysis

Users can analyze recruitment emails using:

- Email subject
- Sender
- Reply-To address
- Email body

The email analyzer evaluates available signals and produces a structured report.

# Risk Assessment

JobShield AI currently uses structured risk categories:

| Category | Meaning |
|---|---|
| `unknown` | Insufficient information to determine a meaningful risk level |
| `low` | Limited risk indicators detected |
| `medium` | Multiple or meaningful risk indicators detected |
| `high` | Significant risk indicators detected |
| `critical` | Strong risk indicators requiring careful review |

The system also produces a numerical risk score from:

```text
0 – 100
```

The risk score is generated by the deterministic analysis engine.

---

# Evidence-Based Analysis

A core design principle is separating **evidence** from interpretation.

Each evidence item can contain:

- Category
- Signal
- Explanation
- Severity
- Status
- Source

Evidence statuses include:

```text
detected
verified
unverified
insufficient_evidence
```

Evidence sources include:

```text
deterministic_analysis
external_verification
user_provided
ai_analysis
```

This allows the application to distinguish between an observed indicator and a confirmed fact.

# Security Model

Security is considered from the beginning of the project rather than added after the UI is complete.

## SSRF Protection

URL analysis validates requested network targets and blocks unsafe destinations.

Protected target classes include:

- Loopback addresses
- Private IP addresses
- Internal network targets
- Cloud metadata endpoints

This is important because URL analysis involves processing user-controlled URLs.

---

## Safe URL Fetching

The URL fetching layer is designed around controlled network access.

Current controls include:

- URL validation
- URL normalization
- Network target validation
- Request timeout
- Redirect validation
- Unsafe destination rejection

---

## Input Validation

API requests use structured Pydantic schemas.

Validation is applied to:

- URL requests
- Message requests
- Email requests
- AI analysis requests
- Configuration values

Invalid input should be rejected before it reaches analysis logic.

---

# AI Architecture

AI is designed as an **optional explanation layer**.

The deterministic analysis engine remains responsible for the existing risk score and evidence.

The AI layer is intended to:

```text
Existing Evidence
       ↓
Structured AI Request
       ↓
AI Provider
       ↓
Structured AI Response
       ↓
Explanation / Findings / Actions
```

The AI should explain available evidence rather than invent independent security findings.

---

## AI Provider Abstraction

The backend currently contains an AI provider abstraction.

The provider interface separates the application from a specific AI vendor.

Current configuration supports:

```text
none
openai
```

The external provider implementation is still under development.

---

## AI Failure Isolation

AI is optional.

If AI is unavailable, deterministic analysis continues to function.

Expected provider failures are handled through:

```text
AIProviderError
```

The application can return a transparent fallback response containing:

- Deterministic evidence
- Existing recommended actions
- AI availability limitation
- Appropriate uncertainty

This prevents AI availability from becoming a dependency for the core security analysis.

# Engineering Principles

The project follows several engineering principles.

## Security First

User-controlled input is treated as untrusted.

## Evidence Over Assumptions

Risk findings should be supported by identifiable signals.

## Deterministic Core

The deterministic analysis engine remains the foundation of the risk assessment.

## AI as an Assistive Layer

AI should explain and organize evidence rather than replace deterministic security checks.

## Fail Safely

External service failures should not unnecessarily break core analysis.

## Test Before Expansion

New functionality should be accompanied by automated tests.

## Small, Reviewable Changes

Development is organized into incremental milestones with tests and Git commits.

# Known Limitations

The current version has several limitations.

### AI

External AI provider integration is not yet implemented.

### Persistence

Analysis results are not yet persisted to PostgreSQL.

### OCR

Screenshot and document OCR functionality is planned but not yet implemented.

### Verification

The current system primarily evaluates available technical and textual indicators. It does not independently verify every recruiter, organization, domain, or employment claim.

### Production

The project is currently under development and is not presented as a production-ready security service.
